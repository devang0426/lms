# AI Workflow Rules

## Approach

Build Studyhall step by step, following the specs. The files in `context/`
define:

- **what** to build: `project-overview.md`
- **how** it is structured: `architecture.md`, `code-standards.md`
- **how** it looks: `ui-context.md`
- **where** we are: `progress-tracker.md`

Always implement against these specs. Do not invent behavior.

`lib/` holds working, tested NitroAI code. Port it: move it, adapt it, keep
its tests. Do not rewrite it from scratch. The per-module plan is in
`architecture.md` under "Where the NitroAI code stands".

## Scoping Rules

- Work on one feature unit at a time. The units are the spec files in
  `context/features/`, built in numbered order; the acceptance criteria
  are the definition of done. Good examples: "Course → module →
  lesson schema + teacher CRUD", "ingest job for PDF", "flashcard review
  screen".
- Prefer small increments you can check over large speculative changes.
- Don't combine unrelated system boundaries in one step.

## When to Split Work

Split an implementation step if it combines any of these:

- UI work and Trigger.dev task work.
- Schema migrations and feature UI (land the migration first).
- Porting a NitroAI module and changing its behavior (port first, keeping
  the tests green, then change).
- More than one role's screens, e.g. a teacher grading view and the
  student's grade view.
- Behavior the context files don't clearly define.

If a change can't be verified end to end quickly, the scope is too big.
Split it.

## Handling Missing Requirements

- Do not invent product behavior the context files don't define. This
  matters most for grading rules, visibility and AI behavior toward
  students.
- If a requirement is ambiguous, settle it in the right context file before
  implementing.
- If a requirement is missing, add it as an open question in
  `progress-tracker.md` before continuing.
- Wireframe placeholders like `[Platform name]`, `[Price / Free]` and
  `[Instructor]` are data slots. They are not copy to hardcode.

## Protected Files

Do not modify these unless told to:

- `LMS Design System & Wireframes.html`: the design source of truth.
- `AGENTS.md`: regenerated by `next dev`.
- `lib/prompts/*` wording. Only change a prompt as a deliberate, versioned
  change (bump `PROMPTS_VERSION`).
- Applied migrations. Add a new migration instead of editing an old one.
- Third-party library internals and `node_modules/`.

## Security Checklist

Check every unit against this list:

- Does any client component import `lib/ai`, `lib/db`, `lib/auth` or `lib/storage`? It must
  not.
- Does every new query check enrollment, course staff or ownership inside the query?
- Is user-supplied HTML or Markdown sanitized before rendering?
- Do user-supplied URLs go through the SSRF guard?
- Does the new AI call log to `ai_usage` and use the cheapest tier that
  works?
- Does anything add a paid service or a recurring cost? If so, ask first;
  the demo runs on free tiers.

## Keeping Docs in Sync

Update the matching context file when an implementation changes any of these:

- System architecture or boundaries: `architecture.md`.
- The storage model or schema decisions: `architecture.md`.
- Code conventions: `code-standards.md`.
- Feature scope: `project-overview.md`.
- Tokens or components: `ui-context.md`.

## Before Moving to the Next Unit

0. If the unit stores student activity (progress, reviews, attempts,
   chats, uploads, submissions), add its cleanup to `RESET_STEPS` in
   `scripts/reset-demo.ts`, so `npm run demo:reset` keeps working.

1. The current unit works end to end within its defined scope.
2. No invariant in `architecture.md` was broken.
3. Tests for the unit pass (`vitest`), and the existing `lib/` tests still
   pass.
4. `progress-tracker.md` shows the completed work.
5. `npm run build` passes.
